## Raise upstream (open-rigs/open-rigs)

Found while building this workflow on 28 Oct 2026. Open each with the line `*Comment/research by Claude, read/edited by Pip.*` and a fix diff where it is short.

- **BehaviorBoard never sets the board's clock, so every Harp timestamp counts from power-on.** Posted 30 Oct 2026 as [open-rigs#6](https://github.com/open-rigs/open-rigs/issues/6). With no clock synchroniser, the board's messages in the `.bin` files and the CSV `Seconds` column are on the power-on count. Within a session they are consistent, but they are not UTC and cannot be compared across sessions or power-cycles. The loggers also name files after Harp time: GEEK-BBOX1 wrote `Camera-Box_1904-01-04T17-00-00.avi` 3.7 days after power-on, with first-row `Seconds` 321,900. This repo now sets the clock itself (`Hardware` > `BehaviorBoard` > `Clock`, 30 Oct 2026): a `SynchronizeTimestamp` on `BehaviorCommands` at the board's first message, with the Harp log and its dump request waiting for the reply (`BoardClockSet`). That works here only because this workflow logs the board late and asks for its own dump. Bonsai.Harp's `Device` (3.6.1) requests the open-time dump before it reads its command input, so a workflow logging from the board's first message still splits each register into a 1904 file and a UTC file, and the module needs the fix. Fix, in `BehaviorBoard.bonsai`:
  - open the `Device` with `DumpRegisters` false;
  - feed it `Concat(SynchronizeTimestamp, OperationControl write with the dump, commands)`, each start-up source ending in `Take(1)`;
  - add a `SynchronizeClock` switch, default on, off where a synchroniser drives the clock input;
  - publish events with `SkipUntil` on the OperationControl reply.

  Tested on GEEK-BBOX1:
  - the switch on and off, with the module alone;
  - this repo's `main.bonsai` with the module swapped in, 1 min from the editor: every file `_2026-10-30T10-00-00`, 3000 == 3000.

  The draft and the patch (against open-rigs main 77094a4) are on GEEK-BBOX1 in `C:\Users\Coen lab\.claude\skills\behaviour-box-performance\`: `open-rigs-issue-clock.md` and `open-rigs-behavior-board-clock.patch`. Once it ships, remove the local `Clock` group and the two `BoardClockSet` gates in `Logging`.
- **CameraTriggerController counts the register-dump reply as a trigger.** Comment on open-rigs#4, which already covers the Camera1 subject parsing the Camera0 register and StartCameras not starting output 1. Both trigger subjects parse every `BehaviorEvents` message, so with `DumpRegisters` on, the Read reply of `Camera0Frame` becomes one extra trigger at startup and the first CSV row comes out early (measured on the box before hw-behaviour-box added the filter). Fix: `FilterMessageType` (Include, Event) before each `Parse`. This repo filters locally in the `Camera` group.
- **RunningWheel takes a Difference in Displacement mode.** New issue. The include sets `EncoderMode` to `Displacement` and still runs `Difference`, `ConvertSigned` and `Accumulate`, which suits `Position` (a running count). The firmware settles it: in Displacement mode `app.c` reports `previous - timer_cnt` and then sets `previous = timer_cnt`, the change over each 2 ms sample, so the chain telescopes to the current sample minus the first, a speed sample rather than a distance. hw-behaviour-box, av-dome's `ActiveExperiments` branch and now this repo all replace the include with an inline copy set to `Position`. Fix: `Position` with the chain as is, or `Displacement` without the `Difference`. Not the same as ucl-open/acquisition#9 (encoder reset racing the subscription).
- **Template: generated files make a deployed clone look changed.** New issue, with the `.gitattributes` lines from this repo. `deploy.ps1` regenerates `*.Generated.cs` (written LF by bonsai.sgen) and the schema JSON and rig template (written CRLF by Python), so with `core.autocrlf=true`, Git for Windows' default, a fresh deploy leaves `git status` reporting the C# file as modified, and with `false` the other two.
- **Template: `deploy.ps1` ignores failures.** New issue. No native step's exit code is checked, and `Setup.ps1` exits 0 whatever Bonsai's restore returned, so a failed deploy exits 0. This repo's fix: `Assert-Success` after each step. `regenerate.py` also ignores `os.system`, which this repo keeps as the template has it (054f823): its sgen runs before `dotnet tool restore`, so on a fresh machine it always fails, and deploy's own checked sgen run catches a real failure.
- **Template: a new project's first deploy writes the C# classes to the project root.** Posted 29 Oct 2026 as [open-rigs#5](https://github.com/open-rigs/open-rigs/issues/5). `deploy.ps1` runs `regenerate-schemas` (which calls `bonsai.sgen`) before `dotnet tool restore`, so on a machine without the tool cached that sgen run fails and never creates `src\Extensions`; `Push-Location .\src\Extensions` then fails and the second sgen writes `<Name>.Generated.cs` to the root, outside what `Extensions.csproj` compiles. Exit 0. Fix: restore tools first, and create `src\Extensions` before `Push-Location`. This repo already creates the folder first (9a118fe), so it only shows a stray "Run dotnet tool restore" line; reorder here too once upstream takes the fix.
- **Template: `pyproject.toml` declares a console script with no module.** New issue. `<project> = "<package>.cli:main"`, but the template has no `cli.py`; running it fails with `ModuleNotFoundError`. Removed here.
- **LogVideo's CSV columns do not exist on TriggeredSpinnaker's trigger overload.** New issue. `LogVideo` selects `Value.ChunkData.ExposureTime` and `.Gain`, which `Bonsai.Spinnaker`'s frame has but `OpenRigs.Video.VideoChunkData` (FrameID and Timestamp only) does not, so the shared logger cannot record the operator's output. Fix: add `ExposureTime` and `Gain` to `VideoChunkData`, copied in the callback with the other two, or drop them from the selector.
- **Template: `Extensions.csproj` compiles C# that Bonsai cannot.** New issue. Bonsai compiles a workflow's `Extensions` folder itself with the .NET Framework's csc (C# 5), but the template's `Extensions.csproj` builds with the SDK's current C#, so `dotnet build` and the editor pass `$"..."` and other C# 6 features that stop the workflow at Start with "Error building script extensions" (this repo's 52cc533, found on GEEK-BBOX1 and fixed in 4b4cb4d). Fix: `<LangVersion>5</LangVersion>`, as this repo now has.
- **A named-device lookup in OpenRigs.Core.** New issue, once this repo's has run on the rig. `RigDevice` (`src\Extensions\RigDevice.cs`) takes one entry out of a rig schema's `Dict[str, Device]` by a `Kind-Instance` name and stops with the entries the file has, where Bonsai's `Index` (vr-corridor-2p's calibrations) says only that the key was not present. av-dome's schema already holds its devices this way and its workflow does not read them yet. Raise with the hyphen point on roadmap#37: the spec splits names at the first underscore, so a device name must not contain one.
- **StreamController names a session the folder does not have.** Posted 30 Oct 2026 as [open-rigs#7](https://github.com/open-rigs/open-rigs/issues/7). `StreamController.bonsai` stamps `date-<start>` from its own `Timestamp` when `RigId` first emits, at Start, while `LogController` stamps the session folder when it is subscribed, which this workflow (like the template) delays behind `RunSettings` and a 1 s `DelaySubscription`. Both format to the second, so on GEEK-BBOX1 the key read `ses-auditkey_date-2026-10-30T17-46-15` for the folder `ses-auditkey_date-2026-10-30T17-46-16`; the earlier session's two listener runs were also a second apart. Fix: build `StreamIdentity`'s key from `PathPrefix` (its last two folders), not a date of its own. This repo did that in an inline copy until c86c6a2 (31 Oct 2026); it now streams with OpenRigs.LiveView's `StreamDevices` (lib-open-rigs), whose key is `ready` until the session folder exists and then the folder's own name, so this repo no longer depends on the upstream fix.
- **Live view has no "recording ended" signal.** Posted 30 Oct 2026 as [open-rigs#8](https://github.com/open-rigs/open-rigs/issues/8), with the smaller points (ports in use stop the workflow at Start, nuspec versions, no access control) and the 30-min results. Nothing in the streams says a run has ended: `elapsed` and video stop, `wheel` carries on until Bonsai closes.
